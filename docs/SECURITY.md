# Безопасность

Что защищаем: персональные данные детей (ФИО, оценки, посещаемость, особые условия), контакты родителей, итоговые оценки (их подмена — главный риск для школы).

## Сделано

**Вход и сеансы**
- Самостоятельной регистрации нет: войти может только человек, которого завела школа (импорт или администратор).
- Вход через Google (OAuth 2.0 + PKCE + проверка state):
  - email должен быть подтверждён;
  - сотрудники и ученики входят только с домена школы (`GOOGLE_ALLOWED_DOMAINS`);
  - Google-аккаунт привязывается к пользователю навсегда: подмена email на другой Google-аккаунт не сработает.
- Пароли хэшируются **argon2id** (параметры OWASP). Политика: не короче 10 символов, без распространённых паролей и имени из email.
- Пароль задаётся только по **одноразовой ссылке**: 256 бит случайности, в базе хранится только SHA-256, срок 72 часа. Новая ссылка аннулирует старую. После установки пароля все прежние сеансы завершаются.
- Сеанс хранится на сервере (`AuthSession`), в cookie лежит случайный токен, в базе — только его хэш.
  - Cookie: `__Host-sid`, HttpOnly, Secure, SameSite=Lax.
  - Сеанс завершается через 14 дней или после 72 часов бездействия.
  - Выход и блокировка пользователя завершают сеансы сразу.
- **Защита от перебора:**
  - лимиты попыток по IP и по email;
  - после 5 ошибок аккаунт блокируется на 15 минут;
  - время ответа и сообщения одинаковые для существующих и несуществующих email.
- Демо-вход без пароля работает **только** при `DEMO_MODE=true`.

**Права доступа**
- Каждая страница и каждое действие проверяет права на сервере (`src/lib/access.ts`); UI только скрывает кнопки.
- Родитель видит только своих подтверждённых детей и только опубликованные оценки. Учитель видит только свои курсы.
- Заблокированный период может менять только координатор **своей** программы. Координатор MYP не правит DP. Выгрузка оценок ограничена программой координатора.
- Автотесты прав: `tests/access.test.ts`.

**Ввод данных**
- Идентификаторы в адресах и формах проверяются (UUID), длина текстов ограничена, нельзя отметить посещаемость несуществующего урока или будущей даты.
- Запросы к БД только через Prisma (параметризованные), SQL-инъекции исключены. React экранирует вывод (XSS). Ошибки показываются кодом, произвольный текст из URL не выводится.
- CSV-выгрузка защищена от формул Excel (`=`, `+`, `-`, `@`).
- Server Actions Next.js проверяют Origin (защита от CSRF). Cookie SameSite=Lax.

**Заголовки HTTP**
- Content-Security-Policy: только собственные ресурсы, `frame-ancestors 'none'`, `form-action 'self'`.
- HSTS, X-Frame-Options: DENY, nosniff, Referrer-Policy: no-referrer (ссылки-приглашения не утекают через Referer), Permissions-Policy.
- Заголовки `X-Powered-By` и `Server` скрыты.

**Инфраструктура**
- PostgreSQL во внутренней сети Docker без выхода в интернет. Порт наружу не открыт, пароль хранится в SCRAM-SHA-256.
- Образ приложения distroless: без shell и пакетного менеджера, работает от непривилегированного пользователя, файловая система только для чтения, все capabilities сброшены, `no-new-privileges`.
- HTTPS с автоматическим обновлением сертификатов (Caddy).
- Ежедневные бэкапы, восстановление проверено (docs/DEPLOY.md, раздел 8).
- Секреты только в `.env.production` (права 600, не в git).

**Журнал аудита** (`AuditLog`): входы, ошибки входа, блокировки, выход, выдача ссылок, установка пароля, блокировка доступа, изменение и публикация итоговых оценок, блокировка периодов, экспорт и импорт.

## Что ещё сделать до работы с реальными данными

1. **Юридическое:**
   - согласие родителей на обработку персональных данных детей;
   - приказ о назначении ответственного за ПДн;
   - договор с хостингом в РК;
   - уведомление в уполномоченный орган, если требуется.
2. **Двухфакторный вход для администраторов и координаторов.** Сейчас его можно получить через Google Workspace с включённой 2FA. Отдельная TOTP-проверка не сделана.
3. **Внешний пентест** перед запуском на всю школу (план R3, неделя 26).
4. **Копия бэкапов на втором сервере в РК** и шифрование бэкапов (например, `age` или `gpg`).
5. **Мониторинг и оповещения** о падении и всплесках ошибок входа.
6. **CSP без `'unsafe-inline'`** для скриптов (через nonce). Требует доработки рендеринга Next.js.
7. **Если будет несколько экземпляров приложения:** перенести лимиты попыток из памяти в Redis или БД. Блокировка аккаунта в БД работает уже сейчас.
8. **Вложения файлов** (R1, недели 7–8): антивирусная проверка и выдача по подписанным ссылкам.

## План реагирования на инцидент (кратко)

1. Заблокировать доступ подозрительным пользователям («Люди» → пользователь → «Заблокировать доступ»).
2. При подозрении на утечку токенов завершить все сеансы: `$C exec db psql -U journal -c 'DELETE FROM "AuthSession"'`.
3. Сменить `POSTGRES_PASSWORD` и секреты Google. Сохранить журналы: `$C logs` и экспорт AuditLog.
4. Оценить, какие данные затронуты. Уведомить руководство школы и, если требует закон, уполномоченный орган и родителей.
5. При повреждении данных восстановить их из последнего чистого бэкапа (docs/DEPLOY.md, раздел 8).
